# KHDS Research Validation

## Purpose

The KHDS validation layer governs how hospitality research becomes reusable knowledge.

This area exists to answer:

* which findings are still observations?
* which findings are strong enough to become Candidates?
* which Candidates deserve Emerging status?
* which patterns need renaming?
* which patterns need narrower boundaries?
* which patterns should be demoted?
* which findings require more evidence before they can be trusted?
* which implementation patterns remain unvalidated?
* when, if ever, should a research-derived pattern become a KHDS Principle?

The validation layer protects KHDS from turning:

interesting observations

into

premature rules.

# What Each Maturity Level Means

## Observed

A potentially useful behaviour has been identified.

Evidence may be:

* isolated
* early
* context-specific
* weakly repeated

It should not yet be treated as a reusable pattern.

---

## Candidate

A behaviour has enough independent evidence to deserve formal continued testing.

A Candidate should have:

* a clear research question
* repeatable behaviour
* identifiable boundaries
* enough evidence that it is not merely one restaurant’s implementation

Candidate does not mean:

proven.

---

## Emerging

A pattern has survived stronger independent repetition and contradiction testing across materially different restaurants.

Emerging means:

the abstraction is becoming stable.

It does not mean:

universal.

---

## Validated

A research-derived pattern has survived broad testing across:

* more restaurants
* more markets
* more hospitality models
* stronger contradictions
* additional evidence types where relevant

Current Validated patterns:

0.

---

## KHDS Principle

A Validated research-derived pattern may eventually become a KHDS Principle if it is:

* durable
* broadly transferable
* strategically meaningful
* operationally useful
* stable enough to inform production decisions

Current research-derived KHDS Principles:

0.

# Validation Outcome Language

When stress-testing a pattern against a restaurant, use:

## Supported

Evidence fits the pattern.

---

## Partially Supported

Some evidence fits but important limitations remain.

---

## Contradicted

Meaningful evidence conflicts with the pattern.

---

## Not Observable

The website cannot provide sufficient evidence.

---

## Not Applicable

The pattern does not meaningfully apply to that hospitality model.

---

# Contradiction Discipline

Contradiction is not something to remove.

If one restaurant contradicts a pattern, ask:

* Is the pattern wrong?
* Is the definition too broad?
* Is the name too narrow?
* Is this a different implementation?
* Is the finding only context-specific?
* Does the pattern need a boundary?

Dishoom produced several cases where:

the behaviour survived

but

the language failed.

That required:

renaming

rather than:

demotion.

---

# Promotion Discipline

Promotion requires evidence that the pattern:

* repeats independently
* survives materially different restaurants
* has stable meaning
* has clear boundaries
* survives contradiction attempts
* is not better explained as part of another pattern

Promotion should become harder as maturity increases.

---

# Candidate Promotion Questions

Before moving a Candidate to Emerging, ask:

1. Does it repeat independently?
2. Does it appear across materially different hospitality models?
3. Has it survived contradiction?
4. Is the abstraction stable?
5. Are the boundaries clear?
6. Is it broader than one implementation?
7. Is it separate from existing patterns?
8. Does it remain useful after generalisation?

If not:

do not promote.

---
